## 决策记录

### 1. LLM 输出格式 → 句子 ID 映射法（不直接输出时间戳）

**决策**：LLM 只输出起始句子 ID 和结束句子 ID（外加判定理由），由代码从 ASR 句子表中查询对应的毫秒级时间戳，映射回视频截取参数。不要让 LLM 自己计算或输出时间戳——这是最稳定的方式，消除 LLM 时间戳幻觉风险。

**输入给 LLM 的内容**：带编号的句子列表，每句包含 `id、StartMs、EndMs、Text`。一次性全部输入（短剧台词量小，1-3 分钟视频约 40-80 句，远低于 DeepSeek 1M 上下文窗口）。

**LLM 输出结构**（通过 `response_format: {type: "json_object"}` + prompt 内嵌 JSON 形状说明强制结构化——DeepSeek 官方 API 不支持 OpenAI 的 `json_schema` 严格模式，只支持 `json_object`，schema 约束靠 prompt 文字描述 + 拿到响应后用 `serde_json` 反序列化校验）：

```
{
  narrative_structure: {        // 先做全局叙事结构定位，给窗口判定提供故事上下文（参考 NarratoAI 短剧混剪 prompt 设计）
    setup: [start_id, end_id],        // 开端：人物/背景交代
    rising_action: [start_id, end_id],// 发展：冲突升级
    climax: [start_id, end_id],       // 高潮：核心冲突/情绪顶点
    resolution: [start_id, end_id]    // 结局：冲突收尾（如无明显结局可为 null）
  },
  start_id: integer,          // 高光窗口起始句子 ID（不强制落在 climax 阶段——广告钩子有时候来自"发展"阶段的一个反差揭示，不一定是全剧最大冲突点）
  end_id: integer,            // 高光窗口结束句子 ID
  reason: string,             // 判定理由
  candidate_sentences: [{     // 可选：扫描时标记的其他候选区间，供代码二次排序
    start_id: integer,
    end_id: integer,
    label: string
  }]
}
```

`narrative_structure` 字段本身不参与后续代码逻辑（代码只用 `start_id`/`end_id`），但让 LLM 先给全剧定位再挑窗口有两个好处：一是强迫模型建立整体故事上下文，不是孤立地在台词堆里找"听起来激烈"的句子，降低选到跟上下文脱节的片段的风险；二是给了一个可调试的中间产物——如果这四个阶段的划分看起来不对，往往说明台词/prompt 本身有问题，不用等到最终窗口选错了才发现。

`candidate_sentences` 字段为可选设计——当 LLM 在扫描台词时发现多个潜在的"精彩片段"，可一并返回，由代码做二次排序（选最长 / 选冲突密度最高 / 选离高潮点最近的）作为备选窗口。这补偿了 LLM 单次判定可能遗漏次优候选窗口的风险。

**窗口时长目标**：约 60 秒，不要求精确到秒。LLM 选出的窗口落在 45-75 秒范围内均视为合格，不强制调整。

### 2. 窗口定位算法 → 锚定高潮点在片段结尾 + 边界 clamp

**决策**：将 LLM 识别出的"最精彩"句子窗口的结束时间锚定为最终片段结尾，向回倒推目标时长。这个设计让高潮在片段末尾戛然而止，形成短剧标准的"悬念式收尾"效果。

**伪代码**：

```
function computeWindow(peakEnd: ms, targetLenMs: ms, videoLenMs: ms):
    // peakEnd — LLM 选出窗口的 EndMs（句子 ID → 查表得到毫秒时间戳）
    // targetLenMs — 目标时长（默认 60000 ms）
    // videoLenMs — 视频总时长（毫秒）

    start = peakEnd - targetLenMs
    end   = peakEnd

    // 边界 clamp
    if start < 0:
        start = 0
        end   = min(targetLenMs, videoLenMs)
        // 此分支下高潮点不再落在片段结尾（极端情况：高潮在视频前几秒内）
        // 在这个罕见边界下接受此妥协，不用复杂逻辑调回——高潮太靠前时"悬念收尾"效果本来也无法成立

    // 兜底：视频本身比目标时长更短
    if videoLenMs <= targetLenMs:
        return (0, videoLenMs)

    return (start, end)
```

**示例验证**（之前聊到的具体数字）：
- `peakEnd = 75s = 75000ms, targetLenMs = 57000ms, videoLenMs = 120s = 120000ms`
- `start = 75000 - 57000 = 18000ms (18s)` → `end = 75000ms (75s)` → `start ≥ 0`，不触发 clamp
- 最终窗口 `[18s, 75s]`，时长 57 秒，落在 45-75s 合格范围内

### 3. Prompt 设计要点

- **System prompt**：固定角色设定，"你是短剧广告投放剪辑师，从带编号的台词列表中先识别开端/发展/高潮/结局的叙事结构作为背景参考，再挑出一段最适合做广告投放钩子的连续片段——目标不是'剧情上最重要的一段'，而是'从未看过这部剧的路人观众刷到后会忍不住点进去看正片'的片段，目标时长约 60 秒"
- **User message**：动态填充每句带编号的时间戳 + 文本（纯文本格式，不需要 JSON 作为 prompt 输入）
- **Few-shot**：可选的优化。如果零 shot 判定质量不够，准备 2-3 个样例（已知精彩片段的对话 + 对应的起止 ID + 判定理由）放入 prompt，但短期不需要，先试零 shot
- **判定理由字段**：必须要求 LLM 附带文本理由，用于未来人工排查和 prompt 质量调优。虽然当前不做审核，但这个字段的排查价值远大于其成本
- **输出前自检清单**（prompt 内嵌，参考 NarratoAI 短剧混剪 prompt 的做法，已按广告钩子标准改写）：要求模型在给出最终答案前自问——①这段片段脱离前后剧情、一个从没看过这部剧的路人观众能不能看懂冲击点在哪里（不依赖此前情节的背景知识）；②是否制造了强烈的悬念/信息缺口（故意不讲透"为什么会这样"），而不是把冲突原委讲完讲清楚；③结尾是否卡在冲突/反转最高点戛然而止，没有给出解决或答案；④时长是否落在 45-75 秒区间。这是提示词工程里常见的自我核对技巧，不增加额外调用——具体能不能减少答非所问的情况，还没有真实数据验证，留给 implementation-plan.md 第 6 步真实素材验证时一并观察

**决策记录 — 单一连续片段 vs 多段情节点混剪**：参考 NarratoAI 时发现它的短剧混剪走的是"挑多个分散但有逻辑关联的情节点，拼成一个完整故事线的混剪"，跟这里的单一连续窗口设计不同。**已确认维持单一连续窗口**，不改成多段拼接——原始需求是"自动截取剪辑产出约 1 分钟高光片段"，单一连续片段更贴合这个目标；多段混剪是不同的产品形态（等于剪出一个浓缩版故事，不是一个"高光时刻"），改动会牵动窗口算法、`compute_window()`、FFmpeg 剪辑逻辑的整体重做，且不是当前需求要的东西。

**决策记录 — 判定标准：叙事精彩 → 广告钩子/引流转化（2026-07-30 修正）**：产品定位澄清为"内部使用软件，产出片段作为广告素材投放到视频平台给短剧引流"（非单纯个人娱乐工具）后，判定标准需要从"剧情上最重要的一段"改为"最能让路人观众瞬间被吸引、忍不住点进去看正片的一段"——这两者不完全等价：叙事上最重要的片段可能需要前情提要才能看懂（比如"他终于说出了三年前的秘密"依赖此前剧情），但广告受众是零上下文的路人，看不懂就没有转化效果；短剧广告投放常用的手法是制造悬念/信息缺口、故意不讲透冲突原委，这跟"把最精彩的地方完整呈现"这个朴素直觉是相反的。**已确认改为广告钩子标准**，system prompt 和自检清单已同步修改。**未改动的部分**：锚定高潮在结尾的窗口算法（`compute_window()`）不需要变——"结尾戛然而止不给答案"本来就是广告钩子的核心要求，跟悬念式收尾的原始设计目标一致，这条设计反而因为这次澄清被进一步验证是对的，不是需要重做的部分。
